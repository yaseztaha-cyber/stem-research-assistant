# v0.5 Technical Report — Answer Quality, Real LLM Evaluation & Human Validation

## 1. Audit (v0.4 preserved)

v0.4 benchmark reproduced (TFIDF+Simple, 100 cases): Recall@5 ≈ 0.95,
Citation ≈ 0.97. All 59 v0.4 tests pass before changes. No retrieval rewrite,
no Qdrant, no unrelated UI. Mock provider kept for deterministic tests.

## 2. V0.4 baseline (100 cases, strict)

Recall@5 0.947, Precision@5 0.650, MRR 0.850, NDCG@5 0.868, Citation 0.97,
Latency ~127 ms (TFIDF+Simple). Dense+CE: Recall 0.953, MRR 0.919,
~2902 ms. Human sample was n=12 (Correctness 3.17, Directness 2.67).

## 3. Real LLM provider

`LLMProvider → MockLLMProvider + OpenAICompatibleProvider (real) +
LocalHFProvider (local)`, configured only by environment:

```env
LLM_PROVIDER=mock|real|local
LLM_MODEL=...  LLM_API_KEY=...  LLM_BASE_URL=https://api.openai.com/v1
LLM_HF_MODEL=HuggingFaceTB/SmolLM2-135M-Instruct
LLM_TEMPERATURE=0.2  LLM_TOP_P=1.0  LLM_MAX_TOKENS=1200
LLM_FALLBACK_TO_MOCK=false
```

Strict mode (`get_llm_provider(strict=True)`) raises `RealLLMUnavailable`
("BENCHMARK FAILED … No score generated") instead of substituting mock —
verified by test. Production falls back only with explicit
`LLM_FALLBACK_TO_MOCK=true`, always logging requested/active/fallback.
Token usage (prompt/completion/total, latency, cost="unavailable" unless the
provider returns pricing — never invented) is captured per generation and
stored on every RAG result. Identity via `get_active_llm_identity()`.

## 4. Mock vs Real experiment

Harness `services/generation_experiment.py::run_ab_case`: one retrieval +
one context shared by all generator arms (controlled); strict refusal for
unavailable providers; per-arm answer/claims/grounding/tokens/latency.

- OpenAI-compatible real LLM: **NOT RUN** — no API key, no local endpoint
  (ConnectError verified). Strict path tested and refuses honestly.
- Local HF (SmolLM2-135M-Instruct, real on-device generator): 6-case ×
  2-retrieval pilot completed (12 local generations, ~1650 tokens/answer,
  20–48 s each on CPU). Outputs were non-answers (fabricated "Dr. John
  Smith" citations, prompt echo, ">10^9 K" nonsense, table fragments;
  preserved in `docs/evaluation/local-ab-results.json`). Excluded from human
  grading as non-informative beyond demonstrating the finding below.
- Local automated groundedness (0.62–0.65) ≈ mock (0.66–0.70) despite visibly
  worse answers — automated groundedness is gameable by vocabulary overlap.

## 5. Retrieval configuration comparison (end-to-end, mock)

From v0.4 strict 100-case matrix: TFIDF+Simple remains default (127 ms);
Dense+CE gains +0.006 recall / +0.069 MRR at 23× latency. Answer Relevance v2
flat 0.608–0.610 across configs — retrieval gains don't reach mock answers.

## 6. Human evaluation dataset

100/100 cases single-graded + 30 double-graded (130 grades, developer
graders, versioned rows, anonymized gold set). Blinded shuffled order
supported in the Grading tab (`GET /api/grading/cases?shuffle=true`).
15 categories covered including deliberately difficult table/contradiction/
derived cases. System-proposed cases were NOT marked validated until graded.

## 7. Human grading results (consensus means, n=100)

| Dimension | Mean |
|---|---|
| Correctness | 1.84 |
| Relevance | 2.22 |
| Completeness | 1.71 |
| Grounding | 2.51 |
| Citation Quality | 2.46 |
| Directness | 2.07 |

Lower than the n=12 sample because the full set includes the hard cases the
mock template fails (wrong-snippet answers, missing derivations,
truncations, spurious conflict footers). This is the true mock-quality
picture — the reason v0.5 exists.

## 8. Pairwise preferences (blinded, TFIDF- vs Dense-evidence answers, n=30)

Tie 19, Dense-evidence preferred 7, TFIDF-evidence preferred 4. When answers
differ (11/30), dense evidence wins 7–4 — weak signal that better evidence
sometimes helps even the mock, but 63% ties show retrieval differences rarely
propagate. Grader was blinded (mapping resolved server-side after grading).

## 9. Automated metric validation (n=100)

| Pair | Spearman ρ |
|---|---|
| Answer v2 vs human relevance | 0.168 (weak) |
| **Answer v3 vs human relevance** | **0.024 (none)** |
| v3 vs human completeness | 0.158 |
| Groundedness vs human grounding | 0.191 (weak) |
| Citation vs human citation | 0.168 (weak; ceiling effect) |
| Coverage vs correctness | 0.120 |

v3 is NOT justified as a replacement: it correlates worse than v2. Cause
identified (not tuned away): v3 strips pipeline conflict footers, but the
mock hides required values inside those footers, destroying value coverage;
its stricter directness collapses variance. **v2 stays the reported metric;
v3 remains experimental.** Additional caveat discovered: benchmark v2/v3 are
computed on *synthetic* answers by default (`use_real_rag=False`), while
humans grade generated answers — automation and human judgment partly measure
different objects.

## 10. Answer-error analysis

Full taxonomy in `docs/evaluation/answer-error-analysis.md` (retrieval-PASS /
answer-FAIL classified: wrong snippet ~25, missing derivation ~12,
truncation ~8, spurious conflict footer ~40 affected, generic opener ~20).
Two systemic issues named for future work (not silently patched):
contradiction detector over-triggers intra-document; mock calculation branch
ignores Pout/Pin-style values.

## 11. Prompt/generation ablation (100 cases, automated, mock)

| Arm | +Component | v2 | v3 | Ground. |
|---|---|---|---|---|
| P1 basic | — | 0.479 | 0.375 | 0.739 |
| P2 query structure | formats | 0.479 | 0.375 | 0.739 |
| P3 evidence hierarchy | ordering | 0.466 | 0.313 | 0.649 |
| P4 answer plan | internal plan | 0.466 | 0.313 | 0.649 |
| P5 validation | labels | 0.466 | 0.313 | 0.649 |

P1=P2 and P3=P4=P5 exactly: the mock only parses Query-Type/Length markers,
so format/plan/validation components are inert for it by construction —
reported as null results, not gains. The P1/P2→P3 shift reflects which source
the first-snippet heuristic lands on. Prompt ablations must be re-run on a
capable real LLM (`prompt_version` param + harness ready).

## 17. Known limitations

n=100 single-grader-developer (bias possible; blinded pairwise mitigates);
TFIDF refit-order ±0.01 run variance; local-model sample only n=6;
synthetic-answer gap in benchmark relevance metrics; citation metric ceiling.

## 18. Final conclusion

- The generator is the binding constraint: retrieval PASS → answer FAIL
  dominates errors, and no retrieval/prompt variation moves mock human
  relevance (pairwise 63% ties, ablation nulls).
- A 135M local model is below the viability bar for grounded RAG prompts.
- The honest end-to-end ranking today: TF-IDF + Simple + Mock for
  speed/reproducibility; Dense+CE only for precision-critical use.
- v2 remains the reported relevance metric (weak but best available); v3
  rejected by its own validation (ρ=0.02).
- Central v0.5 answers: (1) No — with mock/local-135M generators the system
  cannot yet turn correct evidence into reliably useful answers (human
  correctness 1.84/5 on the full distribution). (2) With a capable real LLM
  untested (no credentials), whether retrieval gains transfer remains
  unmeasured — the controlled harness is built and waiting.
